# exec-remote/v1

`motor-protocol` re-exports the caller contract from the pinned crates.io dependency
`cortexkit-exec-remote-types` and owns the SSH/Unix-socket wire types.
The corpus is synthetic: names such as `prefrontal`, `commons`, and `claustrum`
are fictitious specimens, not records of repositories, accounts, or deployments.
The executor never falls back locally; only `refused_before_start` proves the
submitted command did not start. `history_expired` is not a refusal and must
never trigger resubmission.

## Encoding

One frame is a four-byte **big-endian unsigned JSON byte length**, followed by
exactly that many UTF-8 JSON bytes. There is no delimiter or trailing newline.
The discriminator is `type`; fields live inline beside it. Unknown object fields
are ignored. Unknown runner frame discriminators and invalid base64 are errors.
Caller reply and stream enums preserve unknown tags in catch-all variants;
malformed known tags still fail decoding.
`bytes` and `data` use standard padded base64, including non-UTF-8 payloads.
`job_id` and `transfer_id` are UUIDv7 strings. The wire codec validates UUID
syntax; mint-time/retention and UUID-version policy belong to the executor.

Each case has a pretty `.json`, an RFC 8785 `.jcs` (no newline), and a lowercase
64-character `.sha256` over the `.jcs` bytes (no newline). This corpus contains
ASCII strings and small integers only. Generate from the worktree root with
`python3 crates/motor-protocol/tests/generate_vectors.py`; add `--check` to
verify generated bytes without writing files. The Rust golden test
uses an independent RFC 8785 implementation, checks SHA-256, decodes every
frame/reply, and requires re-encoding to preserve every declared field.

Eight `crate-local-unknown-*` additions (six outcomes and two replies) are copied
byte-identically from the published 0.2.0 crate as `.jcs`/`.sha256` pairs, without
pretty `.json` copies. They pin unknown refusal, outcome, stream record, killed,
ran, output stream, prepare outcome, and rebuild result tags. The generator does
not regenerate these published files. Three additional `.jcs`/`.sha256` pairs
from the published 0.2.8 crate pin the typed `lost_to_restart`, `request_rejected`
and `runner_authentication_failed` reasons. Existing vector files retain their
original bytes. `SHA256SUMS` inventories every corpus file except itself and is
refreshed by the generator.

Hello carries `protocol_version` and the optional `started` capability. Missing
or false `started` is the legacy byte-identical Hello; true opts in to sequenced
Started records. Without it the runner omits Started and projects that job's
output sequences and replay cursors down by one, preserving contiguous output
from zero. Jobs without a retained Started use their original sequences. Real
output eviction still carries a projected `truncated_before_seq` boundary.

Hello's optional `gate_jobs` capability enables direct-job priority in motor's
private runner protocol.
ck-motor marks daemon-attested direct-caller runs (`ck motor run`) with
`gate_job: true` only if the runner replies with `gate_jobs: true`. An older
runner receives no mark; shared agent `RunRequest` types have no class field.
False or absent values keep every pre-existing vector byte-identical.

An unknown refusal inside `refused_before_start` still proves no execution.
Unknown outcomes and execution locations never justify a local re-run. Unknown
stream records are skipped, their sequence numbers count toward the resume
cursor, and they are never terminal. An unknown prepare outcome is not prepared;
unknown output labels still retain their bytes and sequence numbers.

## Shapes

- `frames/`: every table frame, both withdrawal answers, all wire refusal forms,
  stdout/stderr, truncated replay, queue-wait override, unknown-ID cancellation,
  and complete two-bundle run/prepare transcripts. A transcript is an array of
  frames, not a frame itself. Its chunk payloads are illustrative binary bytes,
  not fetchable git packs; this corpus pins the framing, not git's pack format.
- `outcomes/`: `{request, stream}` with the caller's env and the complete reply
  stream. Covers every outcome/reason, both kills, pipeline status, lost running
  and queued jobs, and pre-snapshot rejection. No `accepted` precedes the
  `runner_full` terminal. Exactly one terminal ends each stream.
- `replies/`: caller-facing prepare, drop, cancel, and status values without a
  wire frame discriminator. Includes all seven prepare refusal reasons, absent
  workspaces, cold generations and an unreachable server.

`run` has `workspace_key`, `repository_root`, absolute `cwd`, `command`, filtered
`env`, optional `weight_hint` and `timeout` (seconds), resolved
`queue_wait_limit_s`, `snapshot_commit`, expected `tree_hash`, `integration_tip`,
`siblings: [{canonical_path, commit, tree_hash}]`, and
`bundles: [{index, repository, length, sha256}]`. The caller's `RunRequest` instead
has optional queue wait and sibling canonical paths; it cannot supply IDs,
snapshots, hashes or bundles. `prepare` uses `base_commit` instead of a snapshot,
has a `transfer_id`, and otherwise the same snapshot/manifest vocabulary.
`have` and `have_reply` carry `repositories: [{repository, commits}]`.

The terminal's `outcome` is an object discriminated by `type`; exit/signal carry
`code`/`signal`, refusals carry `reason`. `ran`, `tree_hash`, and
`workspace_changes` are always emitted, explicitly null where unavailable.
`workspace_changes` is an array only for `ran: remote`. `killed` and `pipestatus`
are omitted when absent. `outcome_unknown` can describe either a previously
running or a queued job; neither is a before-start proof.

`withdraw_reply` has `outcome: withdrawn|started`. A wire `refusal` has either
`job_id` (runner_full) or `transfer_id` (prepare failure), plus `reason`.
`cancel_reply {job_id}` acknowledges durable idempotent cancellation, including
an unknown-ID tombstone; the terminal is replayed on run/attach, not this reply.
`drop` uses `workspace_key`; its reply has `dropped` and `cancelled_jobs`.
`status_reply` has `queue_depth`, `running_jobs: [{job_id, workspace_key, weight}]`
(including `base:` pseudo-keys), `server_reachable`, `repositories`, and
`rustc_version`. Repository entries have `repository_root`, nullable
`warm_target_age_s`, nullable `published_commit`, and nullable
`last_rebuild_result: building|ok|failed` (null before any rebuild).

Command routing and worker presets belong to callers, not this corpus. These
vectors cover the executor's frames, outcomes, and replies independently of a
caller's routing policy.

## Verification

`cargo test -p motor-protocol` verifies the corpus and codec, including
random bundle chunking, fragmented IO, interleaved heartbeats for run and
prepare, truncation, non-UTF-8 bytes, and additive unknown fields. Bundle digest,
fetch and durable acceptance semantics are implemented by the runner, not the
codec; a decoded transcript alone is not proof of safe execution.

## Queue timing, transfers and retry hints

The runner pushes optional `heartbeat.queue_wait_ms` on the job's existing live
stream, present only while the job waits in the permit queue and absent once it
owns capacity for setup or execution. Its value is elapsed time since verified
bundles were fetched and pinned, not since acceptance. The client subtracts that
elapsed time from its budget to maintain a local deadline, clearing it on a
heartbeat without timing or a disconnected stream. It opens no status channel
for queue timing. `job_status_reply.queue_wait_ms` remains informational for
explicit status requests.

Older clients ignore the additional heartbeat field; older runners send only
plain heartbeats, which never authorize withdrawal. The queue-entered vector
pins zero as a meaningful elapsed time, the queued vector pins elapsed time, and
the queue-state transcript includes a plain heartbeat when capacity is acquired.
The runner still rejects premature withdrawals during upload, fetch or setup.

`withdraw.reason` is optional; absent means queue-wait withdrawal. The only
additional supported reason is `transfer_stalled`, accepted only before dispatch.
Transfers have a 60-second no-progress bound, not an overall duration limit.

`refusal.retry_after_ms` is an optional relative delay on the internal client-runner
frame. ck-motor logs it with the job ID at INFO level; caller-facing refusal
records use `cortexkit-exec-remote-types` and do not include the hint.
Draining admission reports time remaining to the drain
deadline. Disk admission has no scheduled re-probe, so it omits the hint.
Older peers ignore optional fields; older runners omit them. The draining, disk,
queue-wait and stalled-transfer outcome vectors all pin `refused_before_start`
and `ran: none`. These outcomes never authorize retry of an already-started job.

### Workspace lifetime

`run-workspace-kind-head` and `prepare-workspace-kind-head` add the optional
runner-only `workspace_kind: "head"` field. Head workspaces survive idle expiry,
but remain eligible for disk-pressure LRU eviction. The matching `task` vectors
spell out the default explicitly; the original `run` and `prepare` vectors omit
the field and retain task lifetime. Older runners ignore the extra field.
